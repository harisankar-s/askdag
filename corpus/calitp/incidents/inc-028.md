## Summary

On 23 February the unique test on key in tides_gtfs_datasets failed. int_gtfs_quality__naive_organization_service_dataset_full_join joins organizations, services and datasets without any filtering. An agency had added a second service-to-dataset relationship in Airtable for the same dataset (one for each of two services it operates on the same feed), which is allowed, but the join then produced two rows for the dataset with the same key, and that carried through the candidate entities and provider data into tides_gtfs_datasets.

## Impact

- The TIDES export was held for a day because tides_gtfs_datasets failed its unique test.
- No published data was wrong; the test stopped the run.

## Root cause

Duplicate rows from int_gtfs_quality__naive_organization_service_dataset_full_join: the dataset key was built from the dataset alone, not from the dataset and the service relationship.

## Fix

Included the service relationship in the key for the join, rebuilt from int_gtfs_quality__naive_organization_service_dataset_full_join down to tides_gtfs_datasets, and released the export.

## Follow-ups

- Add a uniqueness test on the join's key so the failure shows up where it starts, not four models later.
- rb-11 describes how to trace a uniqueness failure in the TIDES models back to the join.
