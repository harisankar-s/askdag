## Summary

On 7 May a change to dim_stops meant to remove exact duplicate rows within a feed instead removed every stop whose stop_id appeared more than once in any feed version on the same day. Agencies that reuse stop IDs across separate feeds (common for agencies that publish bus and rail separately) lost those stops. Because dim_stops is incremental, only the newly processed feeds were affected, which made the drop look like a real change in service.

## Impact

- About 6% of stops went missing from dim_stops for feeds processed on 6–7 May.
- Stop-level marts and the stop map in the public dashboard showed gaps for two large agencies.
- Rated sev1 because the public dashboard was wrong.

## Root cause

A logic bug: the dedup partitioned by stop_id and date instead of by the feed key and stop_id, so it treated stops from different feeds as duplicates.

## Fix

Fixed the partition to use the feed key, then ran a full refresh of dim_stops (an incremental run would not have restored rows already dropped) and rebuilt the stop-level marts.

## Follow-ups

- Add a test comparing the stop count per feed with the stops.txt row count, allowing for the flagged duplicates.
- Note in the model description that a logic change here needs a full refresh.
