## Summary

On 12 November fct_observed_trips and fct_service_alerts_messages both showed about twice the usual row counts for 23 agencies. int_transit_database__urls_to_gtfs_datasets is meant to map each URL to one GTFS dataset per point in time. After an Airtable clean-up created new dataset records for those agencies without retiring the old ones, both old and new records were current, so every URL matched two datasets and every downstream join doubled.

## Impact

- Rated sev1: observed trips feed the public on-time performance figures, which were briefly published with doubled trip counts.
- Service alert message counts doubled for the same agencies.
- About four hours of RT data had to be rebuilt.

## Root cause

Duplicate rows in int_transit_database__urls_to_gtfs_datasets: the model trusted the Airtable records to have one current dataset per URL. When that broke, it fanned out instead of failing.

## Fix

Retired the old dataset records in Airtable, added a tie-break in the mapping (latest record wins, with a warning), rebuilt the mapping, then fct_observed_trips and fct_service_alerts_messages for the affected days. The public figures were corrected the same afternoon with a note.

## Follow-ups

- Add a uniqueness test on URL and validity window in the mapping; this would have stopped the run before anything was published.
- Hold the public on-time export when the observed trip count changes by more than 25% day over day.
