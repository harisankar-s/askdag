## Summary

On 19 June an analyst found that fct_daily_schedule_feeds had two rows for the same dataset and date for 31 datasets. The model picks the feed version in effect at noon Pacific time. Two feed versions for those datasets had identical validity windows ending exactly at noon, and the comparison used `<=` on both ends, so both versions matched.

## Impact

- Daily counts of scheduled trips were doubled for the 31 datasets on 18–19 June.
- Anyone joining on dataset and date picked up both feeds, so trip totals in two team notebooks were wrong.

## Root cause

Duplicate rows from a boundary condition in fct_daily_schedule_feeds itself. A feed is valid up to the moment the next version starts, so the end of the window must be exclusive. It had been inclusive since the model was written, but it only mattered when a new version started exactly at noon, which first happened after an agency moved its publishing time.

## Fix

Made the window end exclusive, rebuilt fct_daily_schedule_feeds in full, and confirmed one row per dataset and date across all history.

## Follow-ups

- Add a uniqueness test on dataset and date (there was none on that pair).
- The duplicate-check query and the rebuild steps are in rb-09.
