## Summary

On 1 February the uniqueness test on operator and pay window ID in fct_payments_aggregations_enghouse failed. fct_payments_settlements_enghouse had started keeping both the original and the corrected record for settlements that Enghouse resends with a correction, after a change to its dedup on 31 January. int_payments__settlements_to_aggregations_enghouse sums settlements to the payment reference, so corrected settlements were counted twice and some pay windows were split into two rows.

## Impact

- 640 pay windows appeared twice in fct_payments_aggregations_enghouse for January.
- Settled amounts for two operators were overstated by about 1.5% until the fix.

## Root cause

Duplicate rows that started in fct_payments_settlements_enghouse: the dedup key no longer included the correction sequence number, so it kept both versions.

## Fix

Restored the sequence number in the dedup key, rebuilt fct_payments_settlements_enghouse, int_payments__settlements_to_aggregations_enghouse and fct_payments_aggregations_enghouse, and compared January totals with the Enghouse statement.

## Follow-ups

- Add a uniqueness test on settlement ID in the settlements model itself, so the problem stops one step earlier.
- The reconciliation query is in rb-10.
