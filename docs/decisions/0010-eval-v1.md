# 10. Eval v1: exhaustive lineage conformance, then a question set per layer

**Status:** in progress, 2026-11-21. 7a (ground truth and conformance), 7b.1 (golden question set) and 7b.2 (scoring, runner, report) are built; 7c–7d follow.

## Context
Step 7 has to answer, with numbers, how well each layer works: is the lineage walk right, does the LLM read questions correctly (including follow-ups), are the highlights true and useful, and what does each stage cost. The lineage layer has a different bar from the others: it is deterministic, so precision and recall must be 100%, and a miss is a bug.

The first plan was one set of about 30 golden questions for every layer. That mixes two kinds of evaluation:
- The walk is cheap and deterministic, so it can be checked **exhaustively**. Thirty questions touch about 30 roots and would very likely miss a truncation or diamond bug.
- Reading and answering involve the LLM, so they're **sampled**, and each layer needs enough items to mean something.

## Decision (7a)
- **Two evals.** `asklineage eval conformance` checks every walk. The question set (7b) measures reading, resolution, abstention, follow-ups and highlights.
- **Ground truth is independent of the app** (`eval/truth.py`):
  - It uses the standard library only; a test fails if it imports anything else.
  - It reads `depends_on.nodes`, while the parser reads `parent_map`.
  - It walks with a Python BFS, while the app walks with a SQL recursive CTE.
  - What is shared on purpose is the spec: which resource types are nodes (model, seed, snapshot, source) and that self-references are dropped.
  - On Cal-ITP the two edge sources agree exactly: 1,198 edges each way. Both leave out the 1,040 disabled nodes and the 5 exposures.
- **What a walk must match:**
  - the node set, with the root excluded
  - each node's fewest hops
  - every edge between returned nodes
  - `truncated`
  - no node returned twice
- **What it covers:**
  - every node, both directions
  - depths 1, 2, 3, 5 (default) and 25 (max)
  - before any walk, the loaded graph is compared with the manifest's nodes and edges
- **It refuses a stale database.** The latest `manifest_loads` row for the project must have the manifest's `invocation_id`. Otherwise a database loaded from another manifest would show up as false bugs.
- **CI runs conformance on a synthetic manifest** (`tests/synthetic_manifest.py`, about 170 nodes, fixed seed). It has:
  - diamonds whose paths differ in length
  - a hub with many children
  - a 30-model chain (longer than MAX_DEPTH) with a shortcut across it
  - a snapshot
  - test nodes that must be ignored
  - two sources sharing a table name

  The 5-node `mini_manifest.json` can't exercise any of that. A mutation test removes one edge from the truth and checks that the graph check and the walk check both report it, so conformance can't pass by checking nothing.
- `mini_manifest.json` gained `depends_on`, matching its `parent_map`, as real manifests have.

## Trade-offs
| | Sampled golden questions | **Exhaustive conformance** |
|---|---|---|
| Coverage of the walk | about 30 roots | every root, 2 directions, 5 depths (about 8,650 walks on Cal-ITP) |
| Cost | seconds | 8.7 s for 8,650 walks on Cal-ITP |
| Finds | bugs on common paths | edge cases: truncation at the cap, unequal diamonds, deep chains |
| Tests the LLM | yes | no; that's the question set's job |

| | Ground truth from our SQL or parser | **Independent ground truth** |
|---|---|---|
| Code | none extra | about 90 lines of stdlib Python |
| Catches | nothing the code under test gets wrong | CTE bugs, and parser bugs in `parent_map` handling |
| Shared assumptions | everything | only the spec (node types, no self-references), written twice on purpose |

| | `mini_manifest.json` in CI | **Synthetic manifest in CI** |
|---|---|---|
| Size | 5 nodes, depth 2 | about 170 nodes, a chain past MAX_DEPTH |
| Realism | hand-written, readable | generated, so less readable, but every hard case is asserted in a test |
| Licensing | ours | ours; Cal-ITP stays local (AGPL) |

## Consequences
- A lineage miss is now caught in CI on the synthetic graph, and locally on Cal-ITP with one command.
- `truth.py` must change whenever the parser's node rules change (for example, if exposures become nodes). The parser-agreement test makes that visible.
- Lineage stays model-level; column-level ground truth needs SQL parsing (Phase 5).

  - The recursive CTE, the per-level dedup (ADR 0005), the `truncated` check and the parser's `parent_map` handling all agree with the independent BFS.
  - At this cost, the full check can run on every manifest load rather than only in the eval.

- **What the numbers say to do next.** These are proposals; each needs its own decision.
  1. **Choose highlights in code** (ADR 0007 follow-up). Today the LLM adds about 5 s and 1.7k tokens per answer, and does worse than random at choosing. A code rule (for example, one relation per non-majority team, preferring the shortest cross-team path) would score 17/17 on the main measure and cost nothing. The LLM's remaining job would be one sentence per relation, which a template can also write. Its real value would come when descriptions arrive in Phase 2. The option kept open: LLM highlights behind a setting, re-measured with descriptions.
  2. **Close the same-node hole in `check_parse`.** When `same_node` is true but the question contains a node name from the project other than the previous node, reject the reading, the same way highlights reject unmarked node names. This catches the one silent error in this run.
  3. **Recover typo clarifications.** When the only violation is `entity_not_in_question` and the question has exactly one name-like token (backticked, or containing `_` or `.`), resolve that token instead of abstaining. Code takes the name from the question; the LLM only said there was one. Resolution then returns `not_found` with suggestions, as for structured typos.
  4. **Grow the follow-up and typo cases** before quoting rates: 2 new-node follow-ups and 2 typos are anecdotes.
- **Done after the run: proposals 2 and 3**, both in `answer/parse.py` and the flow's `parse` node.
  - **New check rule `same_node_names_another_node`.** On a follow-up, the parse check gets every node name in the project, lower-cased (`node_names`, queried only when there is a previous question). It rejects `same_node=true` when the question names a known node other than the previous one; the retry then copies the name.
    - A name counts when it's written the way dbt names nodes: backticked, or with an underscore or a dot (`name_tokens`). So English words that happen to be node names (`orders`) don't trigger it.
    - It's the same idea as `unmarked_name` in the highlight check (ADR 0007).
  - **Typo recovery** (`recover_reading`). When every attempt fails and the last one's only violation is `entity_not_in_question`, and the question holds exactly one name-like token, the flow resolves that token as written.
    - A typo then gets `not_found` with suggestions, as a structured typo does.
    - A model that swapped in another node's name gets the node the question actually names.
    - With two or more names, or any other violation, it still abstains.
    - ADR 0004 holds: the name comes from the question verbatim, and resolution still never picks a fuzzy match.
    - The response's parse attempts still show both failures, so the recovery is visible.
  - **Rerun, 2026-11-21:** same golden set `06b73c56719d`, commit `cec787f`.

  - **Both fixes did what they were for:**
    - Both typo questions got a clarification with the intended node ranked first: suggestion ranks 1, 1, 1, 1, 1.
    - The `t-typo-choose` turn 2 is no longer blocked.
    - `same_node_names_another_node` fired on the new-node follow-up, and the retry named the right node.
  - **Silent wrong answers went up from 1.8 to 3.6 per 100.** The two silent errors are now both direction errors, which the old behaviour hid:
    - **`t-new-node-and-direction` turn 2,** "And what does ntd_report_validation.all_ntdreports feed?": right node, but upstream, the previous turn's direction. In the first run the same question was read as downstream (with the wrong node).
    - **`t-typo-choose` turn 2:** "What feeds into dim_schedlue_feeds?" was recovered and the choose resumed it, but downstream. Before the fix it abstained, so its direction was never used.   - **A gap in what the eval can see.** `AttemptInfo` keeps a parse attempt's violations but not its reply. ## Decision (7b.1): the golden question set
- **Generated at run time from the local manifest; never committed.** Only the templates (`eval/templates.py`) and the generator (`eval/golden.py`) are committed. Cal-ITP is AGPL, and a committed question file would also go stale whenever the manifest is regenerated.
- **Reproducible from the same manifest.** Nodes are picked by role with fixed rules, ties broken by `unique_id`. Each question's phrasing comes from a seed derived from its own id, so adding an item never changes another one. The set's sha (`asklineage eval golden` prints it) identifies it, and runs are comparable only when the shas match.
- **Roles:**

  | Role | Rule |
  |---|---|
  | hub | model with the most children |
  | deep | model whose farthest ancestor is farthest away |
  | leaf | model with no children and the most parents |
  | seed | seed with the most children |
  | source | source with the most children and a unique table name |
  | typo | the hub's name with two adjacent letters swapped, checked to match no node |
  | multi_team (optional) | model whose two-hop downstream spans the most owners |
  | prefix (optional) | model whose name begins another node's name |
  | shared (optional) | a name several nodes share |

  Required roles that are missing raise an error; optional ones are listed in the set as missing.
- **Expected outcomes come from the manifest and the spec, never from the app.**
  - An exact-name index in `golden.py` restates ADR 0004: an exact id wins, then a single case-insensitive name or `source_name.table` match, then several matches are ambiguous, then not found.
  - Lineage sets are not stored. They come from `truth.walk` when a run is scored.
- **Phrasing.**
  - 2–4 hand-written phrasings per question type, each tagged `seen` (mirrors a parse-prompt example) or `novel`. A gap between the two means the model matches the examples rather than following the rules.
  - `--phrasings all` expands each free-text question into every phrasing.
  - No LLM-written paraphrases: they would need hand review, and a model's own family tends to read them more easily than real users' questions.
- **What's in the set:**
  - 16 structured requests: resolution, lineage and facts, with no LLM needed
  - 15 free-text questions
  - 5 off-topic questions and 1 vague one
  - 9 threads: same-node follow-ups, new-node follow-ups, a pronoun, an off-topic follow-up, a typo then choose, a shared name then choose then follow-up
- **Safe alternatives.** Each expectation may list other outcomes that are safe (for the vague question, a clarification is as good as an abstention). Follow-up turns say whether the parse should reuse the previous node: yes, no, or either.
- **A follow-up that gives no depth keeps the previous depth**, as the flow does (ADR 0009). After "within 2 hops downstream of X", the question "What about upstream of X?" expects depth 2, not the default 5. This was confirmed on review as the intended behaviour, not a quirk the eval happens to accept.
- **Every request is scoped to the manifest's project.** A database holding two projects would otherwise make a name ambiguous that the golden set expects to resolve.

## Decision (7b.2): scoring, runner and report
- **Each turn gets one outcome, worst first:**

  | Outcome | Meaning |
  |---|---|
  | `silent_wrong` | a lineage answer about the wrong node, direction or depth, or one whose table or facts differ from the manifest. The user is told something false and isn't warned. |
  | `safe_wrong` | the wrong clarification or abstention. No answer, but no false one. |
  | `acceptable` | another outcome the golden set lists as safe for this turn |
  | `correct` | |
  | `blocked` | a choose turn whose thread wasn't waiting for a choice; not scored |
  | `error` | the flow raised |

  The headline is **silent wrong answers per 100 turns**, because that's the failure a user can't see.
- **The answer's own walk is always checked against the manifest**, whichever node it chose. So the lineage layer is measured even when reading picked the wrong node. A table or facts mismatch, or an error, is listed as a bug, and `eval run` exits 1. LLM-quality numbers never change the exit code.
- **Layers are scored separately:**
  - lineage table and facts
  - resolution (structured requests only, so reading errors don't mix in): exact, ambiguous (exactly the candidates), not found, expected node in the top-5 suggestions, with ranks
  - reading: answered, node, direction, depth, all three; seen vs novel phrasing
  - abstention: off-topic questions that abstained, and lineage questions that abstained
  - follow-ups: right per "should reuse the previous node: yes, no, either", and how often a named new node was answered about the old one
  - highlight status counts
  - cost per stage: calls, attempts, passed first, retried, p50 and p95 latency, mean tokens
  - wall time per turn
- **Without an LLM**, free-text turns must abstain with `llm_off`, and that is counted. The reading, abstention and follow-up sections need an LLM run.
- **The runner calls `run_ask`**, the entry point `/api/ask` uses. Threads run on `InMemorySaver`; Postgres checkpoints and thread locks have their own tests. One warm-up parse is made before the first scored question and not counted. A turn that raises is rolled back and recorded as `error`, and the run continues.
- **The parse output is not in the response**, so `same_node` is scored by its effect: which node the answer is about. A follow-up that names a new node but is answered about the old one is the silent error the parse check can't catch.
- **Shares are printed as counts**, with a percentage only from 20 turns up.
- **Each run writes `data/eval/runs/<UTC time>-<model>/`** (git-ignored):
  - `golden.json`
  - `results.jsonl`: one turn per line, with the full response
  - `summary.json`: with run metadata
  - `report.md`

  The metadata records the manifest sha256, project and invocation, the golden-set sha, the asklineage commit (`+dirty` when uncommitted), the source commit (`--source-repo`), the provider and model, and a sha of each system prompt.

## Decision (7c): highlight grounding and usefulness
- **`AttemptInfo` gains `rules`**: the rule each violation broke, alongside the existing text. The field is additive, so existing clients keep working.
- **First-attempt failures are split in two:**
  - **hallucination:** `unknown_node`, `wrong_direction`, `no_such_edge`, `no_such_path`, `text_contradicts_direction`
  - **output-rule breach:** numbers, owner wording, unmarked names, invalid output

  Only the first counts toward a hallucination rate. A breach is a formatting cost, not a false statement.
- **A second, independent truth check.** Every highlight the answer keeps is checked against the manifest's edges (direct) or paths (indirect), not against the result's edges. A gap in `grounding.check` would show up here as a contradicted highlight.
- **Usefulness is a code-computed proxy**, over answers whose highlights passed:
  - **main measure:** a node outside the majority owner's team, counted only when the named nodes span more than one team
  - **diagnostics:** team coverage, alphabetical bias (the share of picks that are the alphabetically first direct nodes; lower is better), and reaching past one hop
- **Two baselines, sized to the LLM's pick:**
  - the first named nodes the LLM was shown. The list is rebuilt with `build_facts`, so this is what moving the choice into code would give.
  - a seeded random pick from the same list

  If the code baseline matches or beats the LLM, the LLM is adding sentences, not judgment.
- The proxy is not proof of usefulness. Hand labels check it in 7d.
